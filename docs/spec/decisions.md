## 1. Решения владельца 27.10 (перекрывают brief §8)

### D1 (Q1) — кнопок обратной связи НЕТ, обратная связь — команды

- В дайджесте нет inline-кнопок 👍/👎/🔖. **Раздел «Кнопки» brief §6.1 УСТАРЕЛ**
  (включая предлагавшийся формат `callback_data = fb:{vacancy_id}:{action}`) —
  не реализуется и не проверяется тестами. План §2.5 («кнопки в каждой карточке»)
  и §2.7 читается в новой редакции: обратная связь командами, только статистика.
- Обратная связь: команды `/like <n>`, `/dislike <n>`, `/bookmark <n>`, где `n` —
  сквозной номер карточки из **последнего дайджеста** пользователя; бот помнит
  соответствие «номер → вакансия» последнего дайджеста.
- Точные ответы (копируются дословно):
  - RU: `👍 Учтено` / `👎 Учтено` / `🔖 Сохранено`;
  - EN: `👍 Noted` / `👎 Noted` / `🔖 Saved`.
- Неверный/неизвестный `n` (RU):
  `Не понял номер. Отправьте номер карточки из последнего дайджеста (например: /like 3).`
  (EN: `I didn't get the number. Send the card number from your latest digest (e.g. /like 3).`)
- Статистика пишется (пользователь, вакансия, действие) и **не влияет на выдачу**.
- Следствия для рисков: R5 (привязка действия к конкретной вакансии) закрывается
  однозначным `n`; R26 (подделанные callback) трансформируется в валидацию аргумента
  команды (сценарии `@S47`, `@S49`).

### D2 (Q2) — доставка per-user: максимум один раз

Каждая вакансия доставляется конкретному пользователю не более одного раза
(журнал доставок `(user_id, vacancy_id)`); повторы между дайджестами исключены (R3).
См. также уточнение §5.1 о моменте отметки.

### D3 (Q3) — пустой дайджест: отправляется сообщение

Если подходящих/новых вакансий нет — отправляется ровно одно сообщение:
RU `🔥 Новых вакансий нет`, EN `🔥 No new vacancies`.
**Перекрывает** brief §6.1 («сообщение не отправляется») и brief §7.7.

## 3. Противоречия в brief §6.1 и их разрешение

1. **Возраст вакансии (EN).** В §6.1 перечислены `today` | `yesterday` | `1 day` |
   `{k} days`, при этом `yesterday` и `1 day` обе соответствуют `k = 1` — прямое
   противоречие. Принято: `k = 0` → `today`; `k = 1` → `yesterday`; `k ≥ 2` →
   `{k} days`. Форма `1 day` **не используется**. Причина: зеркало RU-пары
   «сегодня/вчера» и единственный наблюдаемый результат для тестов.
   `[спорное]` — требует подтверждения владельца.
2. **Раздел «Кнопки» (§6.1) устарел** — см. D1.
3. **Зарплата при `min == max`.** В §6.1 нет отдельной формы. Принято: форма
   диапазона `{min} – {max} {cur}` (напр. `150 000 – 150 000 ₽`) — шаблон строгий,
   исключений не вводим.
4. **Спецсимволы шаблонов значимы байт-в-байт** и повторены в feature-файлах:
   `·` = U+00B7 (карточка), `–` = U+2013 в `{min} – {max} {cur}` (с пробелами
   U+0020 по краям), `—` = U+2014 в заголовке дайджеста, разделители разрядов —
   U+0020. `test`/acceptance-тесты обязаны сравнивать строки с точностью до символа.

## 5. Уточнения сценариев, решённые BA (plan молчит)

1. **Момент отметки о доставке (к D2).** `[спорное]` Отметка `(user, vacancy)`
   ставится при формировании дайджеста (в транзакции выборки), а не после
   фактической отправки. Причина: строгий at-most-once — дубль хуже пропуска
   (R3 «похоже на спам»). Следствие: сбой доставки после выборки не приводит к
   повторной отправке этих вакансий.
2. **Пустое сообщение (D3) не сбрасывает соответствие «номер → вакансия»:**
   соответствие обновляется при отправке дайджеста с карточками. Причина: иначе
   команды `/like <n>` ломались бы на следующий день после «пустого» дня.
3. **Валидность `n` (к D1):** целое в диапазоне `1..count` последнего дайджеста
   с карточками. Вне диапазона, не-число, без аргумента, до первого дайджеста —
   точное сообщение об ошибке. Пример в сообщении всегда `/like 3` — фиксированная
   строка, не зависит от команды.
4. **Лишние аргументы** после номера (`/like 3 спам`) игнорируются — обрабатывается
   первый токен.
5. **Повтор действия по карточке** — upsert: одна запись на пару
   (пользователь, вакансия), последнее действие перезаписывает предыдущее.
6. **Возраст (`k`)** = число полных дней от `published_at` до момента сбора
   дайджеста; `published_at` в будущем (смещение tz источника) → `k = 0`
   («сегодня»/`today`). Обоснование R23.
7. **Обрезка `{title}`** до 200 символов (R24): производится по экранированному
   тексту, не разрывая HTML-сущности; при обрезке всегда добавляется `…` так,
   чтобы итог (включая `…`) был ≤ 200 code points; после обрезки HTML остаётся
   валидным. Гарантия «карточка влезает в часть» следует из краткости остальных
   полей (кламп до 100 code points при нормализации). Триггер обрезки и порог —
   решено при реализации, см. §7 «Решено при реализации», п.1.
8. **Нормализация зарплаты (R22):** U+00A0/пробелы/точки в разрядах схлопываются;
   «тыс.»/«млн» → множитель; `min > max` → обмен местами; значения ≤ 0, переполнение
   int64 и неразбираемый мусор → `None` (карточка показывает «Зарплата не указана»);
   валюта вне RUB/USD/EUR → ISO-код (`GBP` и т.п.).
9. **Мин. зарплата пользователя (фильтр):** вакансии **без указанной зарплаты
   проходят** фильтр (lenient). `[спорное]` Причина: «мин. зарплата» — тонкая правка,
   а не жёсткий барьер; жёсткое отсечение теряет релевантные вакансии (R8).
10. **Оценка зарплаты для сравнения:** нижняя граница, если указана, иначе верхняя;
    конвертация в рубли по приблизительным курсам `app/domain/currency.py`.
    Gross/net не разделяются (brief §7.3).
11. **Стоп-слова:** подстрока без учёта регистра в заголовке и названии компании
    (описание не учитывается — экономим релевантность, R13). Стоп-слова пресета и
    пользователя объединяются (правки пользователя глобальны, brief §7.4).
    `[спорное]` по месту поиска (заголовок+компания vs всё описание).
12. **must/nice стек:** все must-фразы должны встречаться в нормализованном тексте
    вакансии (заголовок + описание); каждая nice-фраза даёт баллы скоринга;
    роль/грейд/формат/локация/занятость — по нормализованным полям вакансии.
    Детальные веса скоринга — реализация (`app/filters/rules.py`), но порядок
    сортировки закреплён brief §7.5.
13. **Слот расписания:** слот = локальная дата + время пользователя; отметка слота
    исключает повторную отправку (в т.ч. при рестарте и догоне, R32). Дата в
    заголовке дайджеста — день слота в таймзоне пользователя, формат `dd.mm.yyyy`
    с ведущими нулями.
14. **Агрегация алертов (R16):** «не чаще одного в час на источник» реализовано
    подавлением дублей в скользящем окне 1 часа; подавленные события учитываются
    счётчиком и отображаются в `/admin_health`. Отдельный формат «агрегатного»
    алерта не требуется. Причина: шаблон алерта в §6.1 единственный, расширять
    его без решения владельца нельзя.
15. **DST (R6):** «дыра» локального времени (перевод вперёд) → выпуск в первый
    существующий момент после дыры; двойное локальное время (перевод назад) →
    ровно один выпуск, при первом наступлении слота. Таймзона с ручным UTC-offset —
    без DST, слот срабатывает по фиксированному смещению.
16. **Догоняющее окно:** при восстановлении после простоя отправляются слоты,
    наступившие не более `DIGEST_CATCHUP_MINUTES` (3 ч) назад и ещё не отработанные;
    более старые слоты пропускаются без уведомления.
17. **Retention (R19):** удаляются вакансии с `published_at` строго старше
    `now_utc − RETENTION_DAYS`; ровно 30 дней — остаётся до следующего запуска.
    Удаляются и недоставленные вакансии («дыры» принимаются, R19).
18. **Антиспам (R14/R33):** лимит — 30 действий в скользящее окно 60 секунд;
    превышение → тихий мьют на 10 минут (игнор без ответа); счётчики и мьюты —
    в памяти процесса (сброс при рестарте — принятое ограничение, R33).
19. **Админ-команды** (BA-предложение, `[спорное]` по именам):
    `/admin` (сводка), `/admin_preset_list`, `/admin_preset_add <slug> <name> <json>`,
    `/admin_preset_edit <slug> <json>`, `/admin_preset_del <slug>`, `/admin_stats`
    (пользователи, клики), `/admin_collect` (ручной сбор), `/admin_health`
    (здоровье парсеров + счётчики подавленных алертов). Не-админу — молчаливый
    игнор (не раскрываем существование команд, R17).
20. **AC-18:** напоминание завершить настройку отправляется **один раз** на
    пользователя (после незавершённого `/start`); повторно не напоминаем.
21. **Пресет `backend-other`:** RU-имя `Другие backend-языки` (AC-5) — канон;
    EN-имя `Other backend languages`; каждый пресет показывается с кратким
    описанием состава фильтра (R21).
22. **i18n:** алерты админу всегда RU (brief §7.10); все пользовательские строки,
    включая шаблоны §6.1 и строки §4, — на выбранном языке.

## 7. Решено при реализации (27.10.2026, итерация I-1)

Решения, принятые в ходе реализации и узаконенные BA здесь (R36). Каждое
помечено «решено при реализации»; наблюдаемое поведение уже закрыто тестами.

1. **Обрезка `{title}`: триггер и порог (уточняет §5.7, R24).** «Решено при
   реализации». Формулировка brief §6.1 условная: «Если одна карточка не влезает —
   `{title}` обрезается до 200 символов с `…`». Два прочтения:
   - *(буквальное, brief §6.1)* обрезка применяется только когда карточка целиком
     не влезает в часть 4096 — тогда длинный заголовок остаётся нетронутым,
     пока карточка влезает;
   - *(по примеру @S33, `digest_splitting.feature`)* обрезка обязательна для
     «длинного» заголовка и безотносительно вместимости карточки (пример требует
     ≤ 200 code points с «…» для заголовка в 400 символов с HTML-сущностями,
     который в составе карточки как раз влезает).

   Принято компромиссное прочтение (см. QA `docs/qa/acceptance-map.md` §8):
   **триггер — длина экранированного title > 800 code points** (`TITLE_TRIGGER`),
   **обрезка — до 200 code points включая «…»** (`TITLE_LIMIT`; механика §5.7:
   по экранированному тексту, без разрыва HTML-сущностей, HTML после обрезки
   валиден). Заголовки ≤ 800 code points не обрезаются (P-DIG-04). Оба чтения
   совместимы: после обрезки карточка гарантированно короткая, поэтому условие
   brief §6.1 «не влезает» не наступает; если карточка не влезает в часть и после
   обрезки — `DigestError` (безопасный отказ, R24).
   Поля кроме `{title}` (`company`, `description`) **клампятся на уровне
   нормализации до 100 code points** (`clamp_text`/`FIELD_LIMIT`,
   `app/collectors/base.py`; закрывает вопрос QA §6.10) — это и есть источник
   гарантии «остальные поля короткие», на которую опиралась §5.7.
2. **SQL репозитория: именованный `statement=` + bind-параметры.** «Решено при
   реализации». Все `session.execute(...)` в `app/storage/repo.py` передают
   выражение именованным аргументом `statement=` (не позиционно): детектор
   security-тестов (SEC-06, P-SEC-04) нормализован под kwargs и сканирует
   позиционные аргументы как возможный недоверенный SQL. SQL всегда
   параметризованный (ORM/bind-параметры, `pg_insert ... on_conflict`):
   недоверенный ввод не попадает в текст запроса (SEC-06).
3. **`vacancies.dedup_key` — SHA-256 нормализованных title+company.** «Решено при
   реализации». Ключ = `sha256(normalize_text(f"{title} {company}"))`
   (hex-дайджест), **не сырой текст**: фиксированная длина под unique-индекс,
   устойчивость к регистру/пунктуации/двойным пробелам. Семантика дедупа AC-4
   (brief §7.1, таблица §2) не меняется: дубль ↔ совпадение `canonical_url`
   **или** `dedup_key`; сравниваются нормализованные значения, а не хеш «как есть».
4. **Профиль пользователя хранится в JSONB всегда.** «Решено при реализации».
   `users.profile` — JSONB-словарь (`profile_to_jsonb`) во всех путях записи;
   `Repo.upsert_user`/`set_profile` принимают `Profile` **или** JSONB-dict
   (`Mapping[str, Any]`), чтение — `profile_of` (`app/services/select.py`,
   оба формата) / `profile_from_jsonb`. Причина: единообразие сериализации,
   round-trip `profile_from_jsonb(profile_to_jsonb(p)) == p` (api.md §5).
   Контракт api.md §9 уточнён соответственно; `tests/acceptance/fakes.py`
   (`ModelProfile` — dict с атрибутным доступом) совместим с обоими формами.

### 8.2 Форма callback_data и её валидация

- Форма: `dlg:<step>:<value>` (ASCII), **≤ 64 байт** (жёсткий лимит Telegram);
  `step` — известный шаг (`lang`, `preset`, `format`, `tz`, `size`, `done`,
  страницы городов; точный набор — реализация), `value` — короткий код значения
  (slug пресета / код города / offset / число).
- Обработка: известный `step` + валидное значение → шаг выполняется; любое
  отклонение → единый вежливый отказ (§8.3), состояние не меняется, исключений
  нет (S88).
- Инвариант: ни одна отправленная ботом клавиатура не содержит callback_data
  > 64 байт (S84). Длинные значения (slug пресета 100 символов) кодируются
  коротким кодом — пресет остаётся выбираемым (способ кодирования — реализация).
- Значения из callback никогда не попадают в SQL-текст (параметризация, R44) и
  выводятся в текст сообщений только экранированными (`app.textutil.esc`, §8.6).

### 8.3 Подтверждение callback; устаревший/чужой/подделанный callback

- Каждый `callback_query` получает **немедленный `answer_callback_query`** — до
  завершения обработки шага; «часики» Telegram не показываются (S79).
  Подтверждается и устаревший, и чужой, и невалидный callback.
- «Устаревший» = кнопка не соответствует текущему шагу диалога пользователя
  (шаг уже пройден / диалог завершён или сброшен / у пользователя нет активного
  диалога); «чужой» = нажатие кнопки из диалога другого пользователя. Для
  пользователя устаревший, чужой и подделанный callback неразличимы →
  **единая строка вежливого отказа** (BA-предложение — точной строки в brief
  §6.1 пока нет; ждёт product-manager):
  - RU: `Эта кнопка устарела. Откройте настройки заново (/settings).`
  - EN: `This button is outdated. Open settings again (/settings).`
- Настройки и текущий шаг диалога не изменяются; 500/крашей нет (S80, S81, S88).
- Уточнение D1: R26 («подделанные callback») для обратной связи трансформировался
  в валидацию аргумента команды (S47, S49), но с I-2 возвращается к исходной

## 9. Итерация I-3 (28.10): живая разметка источников (прод-баг I-3)

  `span[data-qa="vacancy-serp__vacancy-employer-text"]`; зарплата —

- **Habr Career:** карточка `class="vacancy-card"`; заголовок

  .basic-salary` (может отсутствовать); дата `time.basic-date[datetime]` ЕСТЬ;

### 9.1 D5 — источник без даты публикации → `published_at` = время сбора

- Если в карточке источника нет даты публикации (выдача hh.ru с 10.2026),
  `published_at` = момент сбора (UTC, tz-aware); карточка **не отбрасывается**.
  Возраст такой вакансии всегда `k = 0` → «сегодня»/`today` (согласовано с
  §5.6 и §3.1: `k = 0` → `today`, форма `1 day` не используется).
- Причина: без fallback карточка либо терялась (текущий парсер отбрасывал
  карточку без даты), либо ломались сортировка `published_at` desc (brief §7.5)
  и retention (§5.17); «сегодня» — честное отражение свежей выдачи.
- Следствия: для hh.ru retention отсчитывается от времени сбора; сортировка по
  `published_at` у таких карточек вырождается в порядок сбора — принято;
  сравнение с более старыми датированными вакансиями корректно (время сбора
  новее любой прошлой даты публикации).

### 9.2 Политика тестовых фикстур источников (обязательна)

1. Фикстуры `tests/data/` для коллекторов ОБЯЗАНЫ создаваться из **живых
   образцов** страниц источников: санитизированные копии реальной выдачи.
2. Санитизация: удаляются скрипты, шум (сторонние счётчики/рекламные блоки
   сервисов) и персональные данные; **структура DOM и маркеры сохраняются**.
3. Каждый файл-фикстура начинается с комментария-шапки: источник (URL выдачи),
   дата съёмки образца и что именно санитизировано.
4. **Синтетика «на глаз» запрещена**: парсер и синтетическая фикстура
   самосогласованы и не отражают реальность — так возник прод-баг I-3
   (зелёные тесты + сломанный прод).
5. Фикстуры обновляются при смене вёрстки источника; признак смены —
   `ParseError`/«пустой разбор» на проде при зелёных тестах.

Причина: единственное надёжное свидетельство контракта разбора — реальная
разметка; синтетическая фикстура проверяет только сама себя.

### 9.3 D6 — промо-карточки hh.ru пропускаются при разборе

- Промо-карточка = ссылка заголовка не ведёт на `/vacancy/` (факт 28.10:
  `https://adsrv.hh.ru/click?...`). Такие карточки **пропускаются**: в кэш не
  попадают, в дедупликации не участвуют, алерта не вызывают (пока разобрана
  хотя бы одна обычная карточка; иначе действует общий контракт §9.5).
- Причина: промо — не вакансия; её URL не канонизируется в `/vacancy/...`,
  попадание в кэш засоряет дайджест и ломает дедуп AC-4 (brief §7.1),
  ухудшает качество выдачи.

### 9.4 Классификация challenge-страниц → `SourceBlocked` (закрывает H2; редакция 2 — решение арбитра 28.10)

**История (редакция 1 устарела).** Первая редакция (28.10) предписывала искать
маркеры challenge-страниц **«во всём теле ответа»** (а не только в первых 4096
байтах). Security review I-3 (F-22, `docs/security/report.md` §10) показал
дефекты этой формулировки в обе стороны:
(1) **ложные срабатывания** — сильные маркеры совпадали с легитимным контентом:
вакансия/компания «Qrator» (реальный работодатель на hh.ru), фраза «just a
moment» в описании → `SourceBlocked` → постоянная потеря источника;
(2) **обход** — маркер, разорванный HTML-комментарием или entity
(`Just a mome<!--x-->nt`, `Just a&nbsp;moment`, `SmartCaptcha` без дефиса), не
матчился, и challenge-страница проходила с неверным диагнозом.
Причина изменения: ложные срабатывания/обход выше. Решение арбитра 28.10
(редакция 2, ниже) заменяет первоначальный контракт; реализовано
(`raise_if_blocked`, `app/collectors/base.py`, F-22), наблюдаемое поведение
закрепляется S94, S96..S98.

- Страница challenge-защиты (DDoS-Guard, QRATOR, smart-captcha, «Just a
  moment») — это **блокировка, а не битая разметка**: `SourceBlocked` → алерт
  `⚠️ Сбор {source}: блокировка/капча` (S94). Классификация как `ParseError`
  маскировала блокировку с IP прод-сервера ложным алертом «ошибка разбора
  разметки» (H2) — остаётся в силе.
- **Нормализация тела перед матчингом** (закрывает обход): снимаются
  HTML-комментарии (незакрытый — до конца), декодируются entity (в т.ч.
  `&nbsp;`), регистр и разделители игнорируются (`SmartCaptcha` ~
  `smart-captcha`) — маркер, разорванный комментарием/entity/дефисом, всё
  равно матчится (S97).
- **Сильные маркеры** (`ddos-guard`, `qrator`, `smart-captcha`, «just a
  moment») дают `SourceBlocked` **только в структурных позициях**: `<script>`,
  `<link>`, cookie-атрибуты, `<title>` (S94).
- **Видимый текст (включая карточки вакансий) НИКОГДА не триггерит
  `SourceBlocked`** (S96): вакансия «Qrator» или фраза «just a moment» в
  описании не должны лишать источник. Это осознанно перекрывает предложение
  security-отчёта F-22 («сильные маркеры — в видимом тексте/`<title>`/атрибутах
  `src`/`href`»): контент вакансий — легитимный текст, а ложный блок хуже
  недодетекта (источник теряется целиком и постоянно, R79).
- **Слабые маркеры** (`captcha`, `access denied`) — только в `<title>`/`<h1>`
  (S98); «captcha» во встроенном JSON-состоянии hh.ru (словари локализации) —
  не блокировка (S96).
- HTTP 403/429 → `SourceBlocked` независимо от тела (как раньше); проверка

### 9.7 D7 — allowlist хостов URL вакансии (F-25)

- URL карточки обязан вести на **хост источника или его поддомен**: hh.ru —
  `hh.ru` и поддомены; Habr Career — `career.habr.com` и `habr.com` с
  поддоменами. Проверка выполняется после канонизации URL (относительные
  ссылки карточек разрешаются относительно base_url источника).
- Чужой хост → карточка **пропускается молча** — как промо (D6, §9.3): в кэш
  не попадает, в дедупликации не участвует, алерта не вызывает (S99).
  Отдельная наблюдаемая категория «чужой хост» не вводится — поведение
  совпадает с промо.
- Страница, на которой **все** карточки пропущены (чужие хосты и/или промо) →
  `ParseError` по общему контракту §9.5 (карточки есть, ни одна не разобрана);
  валидная страница без карточек вообще — по-прежнему `EmptyResult`
  (S100, S95).
- Правила независимы и применяются оба: `adsrv.hh.ru` — поддомен `hh.ru`
  (allowlist проходит), но отсекается промо-правилом D6 (путь не `/vacancy/`);
  поддомены источника (`spb.hh.ru`, `habr.com`) разрешены (S101).
- Причина (F-25, security review 28.10): промо-фильтр D6 проверяет только
  подстроку `/vacancy/` в **пути**, и `https://evil.example/vacancy/1` проходил
  отсечку — фишинг-ссылка под видом вакансии при компрометации источника
  (CWE-601). Не инъекция и не SSRF (URL канонизируется, опасные схемы
  отброшены, ссылки не скачиваются) — именно фишинг-риск в выдаче.
- Сценарии S99..S101; контракт api.md §6/§16.
