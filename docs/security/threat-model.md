# Threat model — it-jobs-finder-bot (I-1, обновления I-2, I-3)

Автор: security-engineer. Дата: 27.10.2026 (I-1); 27.10.2026 — обновление I-2;
28.10.2026 — обновление I-3 (живая разметка коллекторов, §3 «Угрозы I-3»).
Скоуп: итерация I-1 (`docs/plan.md` §2): парсинг HTML hh.ru / Habr Career → PostgreSQL →
дайджест в Telegram; открытая регистрация, команды обратной связи
(`/like|/dislike|/bookmark <n>` — решение владельца Q1, кнопок нет), админ-контур
(`/admin*`), планировщик (APScheduler), Docker Compose.
Обновление I-2 (`docs/plan.md` §8): весь диалог настроек переведён на инлайн-кнопки
aiogram (`callback_query`) — новый недоверенный канал ввода TB-8, угроза SEC-15,
новые риски R60..R62 (`docs/risk-register.md`). Кнопки в дайджесте по-прежнему
отсутствуют (Q1 в силе) — свидетельство обновлено в `docs/security/report.md`.

Методика: STRIDE по границам доверия + OWASP Top 10 (2021) / API Security Top 10 (2023),
ориентир ASVS L1 (приложение без веб-фронтенда, основной ввод — Telegram API и HTML источников).
Риски: `docs/risk-register.md` R43..R52 (security), пересечения с R7/R17/R25/R26/R38 помечены.
Тестовые ID: `SEC-*` (abuse-кейсы), `P-*` (property/fuzz, hypothesis, фиксированный seed
через `derandomize=True`), `A-*`/`U-*`/`E2E-*` — чужие планы митигации.

## 1. Активы

| Актив | Ценность | Угрожающий сценарий |
|---|---|---|
| `BOT_TOKEN` | high: полный контроль бота (рассылка, чтение апдейтов, имитация бота) | утечка → спам-рассылка от имени бота, сбор персональных данных |
| `ADMIN_ID` + админ-контур | high: CRUD пресетов, статистика пользователей, ручной сбор | обход авторизации → изменение фильтров всех пользователей, чтение статистики |
| БД вакансий (кэш hh/Habr) | medium: ядро продукта | SQL-инъекция → порча/удаление кэша, retention-мусор |
| БД пользователей (chat_id, профили, расписание, доставки, feedback) | high: персональные данные (PDP-контур РФ 152-ФЗ — вне скоупа I-1 юридически, но данные идентифицируемы) | утечка/подмена профиля → рассылка чужому получателю, спам |
| Доставляемые сообщения (HTML-дайджесты, алерты) | high: репутация, доставляемость | HTML-инъекция → подмена контента сообщений, Telegram 400, «рассылка мусора» |
| Репутация бота / аккаунт Telegram | high: восстановление после бана дорого | флуд, мусорные сообщения, срабатывание антиспама → жалобы и бан |
| Парсерские сессии/IP сбора | low: блокировки источников (пересекается с R1) | SSRF/агрессивный обход ссылок → блок IP, доступ внутрь инфраструктуры |

## 2. Точки входа и границы доверия

```
[HTML hh.ru / Habr Career] --httpx--> [collectors] --Vacancy--> [repo/PostgreSQL]
[Telegram updates] --aiogram--> [handlers/main] <---> [services] <---> [repo]
[env/.env] --> [app/config.py] --> все компоненты
[APScheduler] --> [services/collect|select|dispatch|scheduler]
[tests/data, файлы] --> [collectors/тестовая обвязка]
```

| Граница доверия | Вход | Уровень доверия | Ключевые риски |
|---|---|---|---|
| TB-1: HTML источников (hh.ru, Habr Career) | title/company/salary/описание/href/даты | **недоверенный** (парсинг чужой разметки) | SEC-01, SEC-02, SEC-09, SEC-12, SEC-14 |
| TB-2: Telegram user input (текст) | тексты команд, аргументы `/like <n>`, `/settings`, `/start`, текстовые шаги диалога (HH:MM, зарплата, стоп-слова, UTC-offset) | **недоверенный** (любой пользователь) | SEC-03, SEC-04, SEC-06, SEC-09, SEC-10, SEC-13 |
| TB-8: Telegram callback_query (инлайн-кнопки диалога, I-2) | `callback_data` вида `dlg:<step>:<value>` (≤64 байт, но размер/содержимое не гарантированы — клиент Telegram недоверен), идентичность нажавшего (`callback_query.from`) | **недоверенный** (любой пользователь может нажать любую кнопку из любого сообщения/пересланной клавиатуры и прислать произвольный `callback_data` нестандартным клиентом) | SEC-15 (→ SEC-05, SEC-06, SEC-09, SEC-10) |
| TB-3: env / `.env` / `.env.example` | `BOT_TOKEN`, `ADMIN_ID`, `DATABASE_URL` | **полунадёжный** (владелец, но попадает в логи/репозиторий) | SEC-08 |
| TB-4: PostgreSQL | значения из TB-1/TB-2, JSONB-профили/пресеты | **полунадёжный** (содержимое отражает недоверенные данные) | SEC-06, SEC-13 |
| TB-5: админ-команды | `/admin`, `/admin_preset_*`, `/admin_stats`, `/admin_collect`, `/admin_health` | **привилегированный вход от недоверенного канала** | SEC-07 |
| TB-6: файловая система (фикстуры `tests/data/`, конфиги, зоны tz через zoneinfo) | пути/имена файлов | недоверенный источник имени → файл | SEC-14 |
| TB-7: зависимости (aiogram, httpx, bs4, SQLAlchemy, asyncpg, APScheduler, alembic, pydantic) | транзитивный код | внешний | SEC-11 |

Изоляция: тесты не открывают сеть и не трогают БД без суффикса `_test` (R41, R29);
production-код ходит в сеть только через переданный `HttpClient` с константными URL источников.

### Сводка по STRIDE

- **Spoofing**: SEC-03, SEC-04, SEC-07 (имитация админа/чужого действия), SEC-15
  (подделка callback: чужой user_id, чужое/старое состояние диалога).
- **Tampering**: SEC-01, SEC-02, SEC-05, SEC-06 (подмена сообщений и данных БД),
  SEC-15 (инъекция в `value` callback_data, применение чужих значений).
- **Repudiation**: частично — подделка feedback (SEC-04) искажает статистику админа; журнал
  `parse_runs` фиксирует сборы (детерминированная сводка, не полный audit log — принято I-1).
- **Information Disclosure**: SEC-08 (секреты), SEC-07 (статистика/пресеты), утечка внутренних
  деталей в тексты ошибок — см. §5.
- **Denial of Service**: SEC-09, SEC-10 (+ R35 «тяжёлые страницы», вне security-нумерации),
  SEC-15 (флуд callback'ами, oversized data).
- **Elevation of Privilege**: SEC-07 (главный), SEC-13, SEC-11, SEC-15 (действие от имени
  чужого диалога/чужого шага).

| A10 SSRF | URL из вакансий | SEC-12 |

## 5. Требования к реализации, закреплённые security-тестами

Это «контракт безопасности» поверх `docs/spec/api.md`; тесты в `tests/security/` падают,
пока требования не выполнены. При расхождении — обсуждение на ревью, **тесты не ослаблять**.

1. `app.textutil.esc` никогда не бросает исключений и никогда не добавляет сырых `<`/`>`
   (round-trip: `html.unescape(esc(t)) == t`); `esc_attr` дополнительно экранирует `"`.
2. `canonicalize_url`: результат либо http/https-URL, либо строка без схемы; никогда —
   `javascript:`/`data:`/`file:`; без `"`, `'`, `<`, `>`, пробелов и управляющих символов.
3. `profile_from_jsonb`/`load_filter`: только `ValueError` на битых данных (никаких
   `TypeError`/`AttributeError`/`RecursionError`/исключений парсинга); в `app/` нет
   `pickle`/`eval`/`exec`/`yaml.load`/`marshal`.
4. SQL-текст запросов никогда не содержит значений из недоверенного ввода (только bind-
   параметры); запрещён f-string/`.format()`/`%` внутри `text()`/`execute()` с SQL-ключевыми
   словами.
5. `Settings`: `admin_id` — `int`; `repr(settings)`/`str(settings)` не содержат значения
   `bot_token`; текст ошибки `ValidationError` не содержит значения `bot_token`.
6. `parse_hhmm`/`parse_tz` на любом входе дают `time`/tz или `ValueError` (и ничего иного);
   `parse_tz` отклоняет пути (`../`, `/etc/passwd`, NUL) — path traversal через zoneinfo.
7. `select_digest(limit=...)`/`Profile.digest_size`: строго 1..50, иначе `ValueError`.
8. Тестовый вход для проверки хендлеров — `BotHarness` (`tests/e2e/helpers.py`, api.md §15):
   минимальный API, который фиксируют security-тесты:
   - `async with BotHarness() as h: await h.send(text, user_id=...); ответы = await h.sent()`
     (объекты с `.text` либо строки) — текстовый вход (TB-2);
   - **I-2, callback-канал (TB-8)**: `await h.tap(data, user=None)` — симуляция нажатия
     кнопки/присылки `callback_query` с `callback_data=data` от `user` (`None` —
     пользователь последнего `send`/`tap`; для подделанных callback тесты передают
     чужой `user_id` явно); ответы — как у `send` (через `h.sent()`);
   - **I-2**: `h.answers()` — `answer_callback_query`'ы последнего `tap`: объекты с
     `.text` (пустая строка = подтверждение без текста) либо строки; **ровно один
     элемент на каждый callback** (включая устаревший/чужой/невалидный и флуд —
     «часиков» нет никогда). Порядок «answer до ответа бота» (S79) проверяют
     тесты qa-engineer (A-DLG-03/U-DLG-02); security-контур фиксирует «ровно один
     answer на callback, включая путь отказа».
   Если software-engineer выберет другой API — согласовать на ревью, security-тесты не
   ослаблять. Низкоуровневый вход (implementation detail, НЕ закреплён) — за
   `BotHarness.tap` может стоять любой метод `BotCore`; property/fuzz (P-SEC-06)
   ходят только через `BotHarness.tap`/`answers`.
   - **I-2-fix, chat-граница (F-15, TB-2/TB-8)**: `BotHarness` изолирован от
     chat-контекста (`chat.type`), поэтому security-тесты F-15 входят через
     `app.bot.handlers.handle_message(message, bot_core)` /
     `handle_callback_query(callback, bot_core)` с синтетическими
     aiogram-подобными объектами `tests/security/support.py`
     (`FakeMessage`/`FakeCallback`/`FakeChat` — записывают всё опубликованное
     в чат и все `answer_callback_query`). Инварианты, которые фиксируют тесты:
     диалог (текст и callback) работает только при подтверждённом
     `chat.type == "private"`; неподтверждённый/спуфленный чат (нет `chat`/
     `from_user`, неизвестный `type`) — fail-closed (ничего не публикуется и не
     обрабатывается); callback из группы/неподтверждённого чата → ровно один
     молчаливый `answer` (без текста), настройки пользователя не публикуются.
9. Общий хелпер допустимых тегов `tests/html_check.py` (владелец — software-engineer):
   security-тесты зовут его как `html_check.check_html(text) -> list[str]` (пустой список —
   нарушений нет). Второй, независимый oracle — локальный в `tests/security/support.py`
   (defense in depth: тесты не полагаются на один общий код с реализацией).
   Метки кнопок инлайн-клавиатуры (I-2) — plain text (не HTML): экранированию через
   `esc` подлежит весь HTML-текст сообщений шагов диалога, включая имена пресетов
   из админского ввода (SEC-15/SEC-05).

## 6. Митигации без автоматических тестов (code review / эксплуатация)

- Коллекторы обязаны выполнять HTTP-запросы **только** к константным URL источников
  (SSRF: ссылки из вакансий не скачиваются) — проверяется на ревью и grep'ом по `app/collectors/`.
- HTTPS к источникам; без клиентских сертификатов/прокси (вне I-1).
- Ротация `BOT_TOKEN` при любом подозрении на утечку (BotFather `/revoke`); деплой-секреты
  не попадают в образ Docker (`.dockerignore`, env при запуске).
- Резервное копирование БД и ограничение доступа к PostgreSQL сетью Compose (только `bot`)
  — ответственность devops-sre, статическая проверка docker-compose.
- Минимальные привилегии: бот не имеет права чужие чаты, админ-контур — только команды бота
  (веб-админки нет).

## 7. Вне скоупа / отложено

- Отказ в обслуживании на уровне VPS (rate limit на уровне iptables/nginx) — devops.
- Юридический контур персональных данных (152-ФЗ) — product-manager, вне I-1.
- Компрометация аккаунта разработчика/CI (supply chain build) — CI вне I-1 (plan §9.8).
- Чтение Telegram-каналов, прокси-пул, антикапча — отложены (plan §4.2); при появлении
  threat model пересматривается (новые границы доверия).
